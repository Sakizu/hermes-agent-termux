# Termux Port Audit — 2026-10-05

**Scope:** full Termux/Android compatibility audit of this repository —
26 patches (`patches/`), build scripts (`scripts/`), packaging (`DEBIAN/`,
`launchers/`), CI workflows (`.github/workflows/`), and the shipped reference
`.deb` (`hermes-agent_0.0.0+1298c8e_aarch64.deb`).

**Target:** aarch64, Android API 24+ (Android 7+), Termux
(`PREFIX=/data/data/com.termux/files/usr`), Python 3.14, one `.deb` per arch.

**Method:** 4 parallel slice workers (patch completeness, patch correctness,
scripts+packaging cold review, runtime-dependency verification), followed by
4 adversarial cross-reviewers, each assigned a *different* slice than they
audited, tasked solely with breaking the Phase-1 conclusions. Every claim
below carries file:line evidence; anything unverifiable is labeled
UNVERIFIED, never inferred.

**Upstream basis:** NousResearch/hermes-agent @ `1298c8e74baa73e1a2b90124228d017261ac6bc4`.

## Verdict

| Severity | Count | Meaning |
|---|---|---|
| P0 | 4 | Build cannot succeed as written (all in `scripts/` / workflow contract) |
| P1 | 11 | Will break or silently degrade on the phone / in CI |
| P2/P3 | 31 | Hygiene, polish, latent issues |

The 26 patches themselves are in excellent shape: **26/26 reproduce the
known-good patched tree byte-for-byte, 25 verified clean, 0 redundant**
(upstream's in-tree Termux toolchain covers none of the 26 patched paths —
verified per-patch). The full-tree incompatibility hunt found **no P0/P1
misses** — the patch set is complete for the `.py` runtime. Every P0 is in
the *build automation*, which has never run end-to-end: **the CI pipeline as
written cannot produce a `.deb` today.** Fixing the 4 P0s is the gating item
for the production-ready build.

## P0 — build breaks (fix before any build attempt)

### P0-1. `scripts/00-toolchain.sh:14` — `REPO_ROOT` is one level too high

- **Evidence:** `00-toolchain.sh:14` computes
  `REPO_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"`. All four sibling scripts
  use `"$SCRIPT_DIR/.."` (`build.sh:22`, `10-wheels-c.sh:18`,
  `11-wheels-rust.sh:16`, `30-assemble.sh:19`).
- **What's wrong:** line 16 `source "$REPO_ROOT/versions.env"` resolves to
  `<repo>/../versions.env`, which does not exist (verified) → under
  `set -eu` the script aborts immediately. Nothing downstream runs. Line 58's
  `termux_deb.py` path is wrong for the same reason.
- **Fix (exact):**
  ```diff
  -REPO_ROOT="$(cd "$SCRIPT_DIR/../.." && pwd)"
  +REPO_ROOT="$(cd "$SCRIPT_DIR/.." && pwd)"
  ```
- **Tradeoff:** none. Typo-class bug; all sibling scripts agree.

### P0-2. `scripts/00-toolchain.sh:73` — patchelf extraction `mv` fails (reproduced)

- **Evidence:** line 73:
  ```bash
  (cd tools && unzip -o -q patchelf-*.whl '*/patchelf' && mv */patchelf . && chmod +x patchelf)
  ```
  Reproduced empirically: `patchelf==0.19.1` extracts to
  `patchelf-0.19.1.0.data/scripts/patchelf` (two levels deep; the unzip
  `'*/patchelf'` pattern crosses `/`, but the *shell* glob `*/patchelf`
  matches only one level) → `mv: cannot stat '*/patchelf'` (rc=1) →
  `set -eu` aborts. The `[ ! -x "tools/patchelf" ]` guard (line 69) means
  every re-run retries and fails identically.
- **Fix (exact):**
  ```diff
  -    (cd tools && unzip -o -q patchelf-*.whl '*/patchelf' && mv */patchelf . && chmod +x patchelf)
  +    (cd tools && unzip -o -q patchelf-*.whl '*/patchelf' \
  +        && mv patchelf-*.data/scripts/patchelf . && rm -rf patchelf-*.data \
  +        && chmod +x patchelf)
  ```
- **Tradeoff:** none for correctness. The `patchelf-*.data` glob assumes the
  standard wheel `.data` layout; `find tools -name patchelf -type f` is an
  equivalent alternative. Either is strictly better than the one-level
  assumption. (Also consider pinning the full `0.19.1.0` version string;
  pip accepts `==0.19.1`.)

### P0-3. `scripts/11-wheels-rust.sh:31-41` — rustup installs to the wrong home

- **Evidence:** line 31 `export HERMES_CARGO_HOME="$HERMES_WORK/cargo-home"`;
  line 37 checks `$HERMES_CARGO_HOME/bin/rustc`; lines 38–39 pipe
  `https://sh.rustup.rs` into sh; line 41 invokes
  `$HERMES_CARGO_HOME/bin/rustup`. `CARGO_HOME` is **never set** anywhere in
  the repo (repo-wide grep confirms) — rustup's installer therefore lands in
  `~/.cargo`, the check never passes, and the `rustup` invocation exits 127
  → abort before any wheel builds. `scripts/lib/env-rust.sh:21` also puts
  `$HERMES_CARGO_HOME/bin` on PATH, so even a `~/.cargo` install is invisible.
- **Fix (exact):** in `11-wheels-rust.sh` before the rustup block, or better
  in `scripts/lib/env-rust.sh` next to the other exports:
  ```bash
  export CARGO_HOME="$HERMES_CARGO_HOME"
  export RUSTUP_HOME="$HERMES_CARGO_HOME"
  ```
- **Tradeoff:** none for correctness. Keeps the work dir self-contained under
  `$HERMES_WORK`, which is the evident intent (and avoids touching the
  runner's `~/.cargo`).

### P0-4. `scripts/build.sh` ignores the workflow's `HERMES_WORK` — CI fails *after* a successful build

- **Evidence:** `.github/workflows/build-deb.yml:37` sets
  `HERMES_WORK: ${{ runner.temp }}/hermes-work` and calls
  `bash scripts/build.sh --ref …` *without* `--work`. `build.sh`
  unconditionally recomputes `HERMES_WORK` from `--work` (default
  `<repo>/.build-work`). `upload-artifact` (`:116`, `if-no-files-found:
  error`) and `gh release create` (`:128`) glob
  `${{ runner.temp }}/hermes-work/hermes-agent_*_aarch64.deb` — which is
  empty, because the `.deb` landed in `<repo>/.build-work/`. CI goes red
  after a fully successful build, even with P0-1–P0-3 fixed. (Found by the
  adversarial reviewer; Phase-1 declared this contract "coherent" without
  checking it.)
- **Fix — option A (recommended):** honor a pre-set `HERMES_WORK`, mirroring
  the `DEB_VERSION` precedent already in `build.sh`:
  ```diff
  -WORK="$REPO_ROOT/.build-work"
  +WORK="${HERMES_WORK:-$REPO_ROOT/.build-work}"
  ```
  (then absolutize as today).
  **Option B:** pass `--work "$HERMES_WORK"` in the workflow's build step.
- **Tradeoff:** none material. Option A keeps one code path and matches the
  established `DEB_VERSION` pattern; option B keeps `build.sh` authoritative
  over its work dir. Either closes the hole — pick one, not both.

## P1 — will break or silently degrade

### P1-1. Patch 14: `pkg install espeak-ng` — no such Termux package

- **Evidence:** `patches/14-hermes_cli_setup_tts.py.patch` →
  `hermes_cli/setup_tts.py:33`:
  `"android": ("Install with: pkg install espeak-ng", ["pkg", "install", "espeak-ng"])`.
  Verified against primary sources: termux-packages ships **`espeak`**
  1.52.0 (built from the espeak-ng upstream); `packages/espeak-ng` → 404.
  The Termux `espeak` package provides the `espeak-ng` binary, so the probe
  at `setup_tts.py:45` (`shutil.which("espeak-ng") or shutil.which("espeak")`)
  works — only the install hint/argv is wrong. On the phone,
  `hermes setup tts` would print a bogus hint and run a failing
  `pkg install` (caught by `except (CalledProcessError, FileNotFoundError)`
  at `setup_tts.py:51-54` → broken setup flow, not a crash).
- **Fix (exact, one word):**
  ```diff
  -    "android": ("Install with: pkg install espeak-ng", ["pkg", "install", "espeak-ng"]),
  +    "android": ("Install with: pkg install espeak", ["pkg", "install", "espeak"]),
  ```
- **Tradeoff:** none. Strictly a correction; no behavior change on other
  platforms. (Note: the android entry itself is still needed — the pristine
  fallback would have run `sudo apt install -y espeak-ng`, doubly broken on
  Termux.)

### P1-2. `Depends: python (>= 3.14)` has no upper bound — next Termux python minor bricks native imports

- **Evidence:** `DEBIAN/control.in` → `Depends: python (>= 3.14), …`.
  Every shipped extension filename encodes the ABI:
  `_cffi_backend.cpython-314-aarch64-linux-android.so`,
  `_pillow_heif.cpython-314-…`, `parser.cpython-314-…`,
  `jiter.cpython-314-…`, `_speedups.cpython-314-…`,
  `_pydantic_core.cpython-314-…`, and 10 of 13 `.so` files NEEDED-link
  `libpython3.14.so` (readelf-verified). When Termux ships python 3.15,
  `apt upgrade` satisfies `python (>= 3.14)` with 3.15,
  `libpython3.14.so` disappears, and **all** native imports fail at once —
  on a routine `pkg upgrade`. (The abi3-tagged modules still NEEDED-link
  `libpython3.14.so` in 4 of 5 cases, so they break too.)
- **Fix:** `Depends: python (>= 3.14), python (<< 3.15)` (apt supports this
  range syntax), and rebuild the `.deb` per CPython minor release as a
  matter of policy.
- **Tradeoff:** the upper bound means a python 3.15 Termux upgrade will hold
  back *this* package until a rebuilt `.deb` is published — a deliberate,
  visible pin rather than a silent mass import failure. The alternative
  (no bound) trades a clean upgrade path for certain breakage later. The
  bound is the right trade.

### P1-3. `python-pillow` declared with no version bound

- **Evidence:** `DEBIAN/control.in` declares `python-pillow` unversioned; the
  `.deb` ships zero Pillow files (no `site/PIL/`), so runtime uses whatever
  Termux ships (12.3.0 as of 2026-10-05). `_pillow_heif` talks to Pillow
  purely through the Python API (its NEEDED links are only `libheif.so.1` +
  `libpython3.14.so`), so a future Pillow major API change could break image
  code paths — at *use* time, not import time.
- **Fix:** `python-pillow (>= 11.1.0)` (matches `pillow_heif` 1.6.0's own
  declared floor) or `(>= 12.3.0)` (matches the tested version); record the
  tested Pillow in the build notes.
- **Tradeoff:** a `>=`-only lower bound is the safe shape — it can only
  block installs if Termux regresses Pillow backward (rare). Leaving it
  unpinned risks a silent runtime break on a Pillow major bump. Blast
  radius is smaller than it looks: the app's Pillow API surface
  (`Image.open/convert/resize/LANCZOS/quantize`, `ImageDraw`, `ImageFont`,
  `ImageFilter`, `ImageOps`, `ImageEnhance`, `ImageChops`) is ancient-stable.

### P1-4. System `python3` assumed to have `packaging`; nothing installs it

- **Evidence:** `scripts/lib/native_deps.py` and `scripts/lib/closure.py`
  do `from packaging.markers import Marker` (exit 2 if missing). Invoked
  with bare `python3` at `11-wheels-rust.sh:94`, `30-assemble.sh:49`,
  `30-assemble.sh:65`. No workflow step or script installs `packaging`
  into system python3 (the runner-image manifest could not confirm its
  presence; the dependency is undeclared either way). Failure is loud
  (exit 2) but kills the build mid-pipeline.
- **Fix:** add `python3 -m pip install -q packaging` to the workflow's
  "Install system dependencies" step, or route the three call sites through
  the existing venv python.
- **Tradeoff:** one extra pip install (~seconds) vs. touching three call
  sites. The pip route is cheaper and just as correct.

### P1-5. `scripts/10-wheels-c.sh:85-95` — pillow-heif re-patch guard aborts re-runs

- **Evidence:** the guard `if grep -q '"/usr/include"' setup.py` tests for
  *patchable content*, but the patch only rewrites the
  `if sys.platform.startswith("linux"):` condition line — the body still
  contains `"/usr/include"` strings. On a re-run (`$srcdir` already exists,
  so the sdist is *not* re-extracted despite the comment at lines 82–84),
  grep still matches, the re-sub finds no match, and
  `assert s2 != s` (line 93) raises → build aborts. First run works; any
  same-`--work` re-run fails.
- **Fix:** guard on the already-patched marker instead:
  ```diff
  -            if grep -q '"/usr/include"' setup.py; then
  +            if grep -q 'HERMES_CROSS_BUILD' setup.py; then
  +                echo "pillow-heif setup.py already patched"
  +            elif grep -q '"/usr/include"' setup.py; then
  ```
  and correct the stale "re-extracted fresh" comment.
- **Tradeoff:** string-marker idempotency is slightly less precise than a
  stamp file, but matches the surrounding style and is strictly more
  correct than the current guard.

### P1-6. `scripts/20-tui.sh:17` — full TUI rebuild on every run

- **Evidence:** `rm -rf "$TUI_WORK"` unconditionally, then `cp -a` +
  `npm ci` + esbuild. `build.sh`'s header promises "Re-running with the same
  --work dir is cheap: every step skips work that is already done" — this
  step skips nothing.
- **Fix:** guard on a stamp — skip when
  `$TUI_WORK/hermes_cli/tui_dist/entry.js` exists, keyed on `$UPSTREAM_REF`
  (the ref is part of the work-dir lifecycle via the fresh clone).
- **Tradeoff:** stamp-invalidation logic can go stale, but keying on the
  upstream ref bounds the risk; the win is minutes per re-run.

### P1-7. `scripts/11-wheels-rust.sh:99-113` — maturin rebuilds all five crates every run

- **Evidence:** sdist extraction is guarded (`if [ ! -d "$srcdir" ]`), but
  the `maturin build --release` loop runs unconditionally. Cargo's target
  dir persists (incremental), but cryptography re-link alone is minutes.
- **Fix:** skip when a wheel for `${name}-${ver}` already exists in
  `$R_DIR/dist/`, mirroring the extraction-guard style.
- **Tradeoff:** a stale wheel could mask a toolchain change; acceptable
  (work dir is per-build) or key the guard on a toolchain stamp.

### P1-8. `scripts/30-assemble.sh:67-82` — resvg-py wheel downloaded with no hash check

- **Evidence:** version comes from `native_deps.py` (uv.lock), filename from
  the PyPI JSON API, fetched via the simple index with **no sha256
  verification** — every other artifact in the pipeline is sha256-pinned.
  The JSON API response already contains `digests.sha256`; it is ignored.
  Supply-chain gap in the final packaging step.
- **Fix:** capture sha256 from the JSON API and verify after download;
  prefer the JSON API's `url` field over re-scraping the simple index.
- **Tradeoff:** a few more lines; strictly increases integrity. None
  against.

### P1-9. `scripts/lib/assemble_wheel.py:97-98` — zero-extension wheel only warns

- **Evidence:** `if renamed == 0:` prints a stderr warning and returns 0. If
  `build/lib.*` didn't materialize (e.g. the `buildlib="$(echo
  build/lib.*)"` glob at `10-wheels-c.sh:104,142` failed to expand and
  passed the literal pattern), a pure-Python wheel ships under a native tag
  and `verify_so` passes vacuously. A broken wheel ships silently.
- **Fix:** `return 1` instead of warn (all five C-track packages must
  contain extensions).
- **Tradeoff:** none for these packages.

### P1-10. `publish.yml:120-121` — rclone pool-copy failure is masked

- **Evidence:**
  ```bash
  rclone copy "r2:${R2_BUCKET}/debs" "$REPO/debs" 2>/dev/null \
    || echo "no existing pool in R2 (first publish)"
  ```
  Any genuine failure (auth, network, partial transfer) is swallowed and
  misreported as "first publish". The `Packages` index is then built from
  an incomplete pool and uploaded — older `.deb`s silently drop out of the
  index, breaking `apt upgrade` continuity on phones.
- **Fix:** distinguish empty-bucket from errors:
  ```bash
  if rclone lsf "r2:${R2_BUCKET}/debs" >/dev/null 2>&1; then
      rclone copy "r2:${R2_BUCKET}/debs" "$REPO/debs"
  else
      echo "no existing pool in R2 (first publish)"
  fi
  ```
- **Tradeoff:** one extra `lsf` round trip; strictly more correct.

### P1-11. `publish.yml` trigger can never fire from `build-deb.yml`

- **Evidence:** `publish.yml` uses `on: release: types: [published]`, but
  `build-deb.yml:124` creates the release via `gh release create` with
  `GITHUB_TOKEN`. GitHub does not trigger workflows from `GITHUB_TOKEN`
  events (documented anti-loop behavior). The intended
  build → release → APT-publish chain is broken; `publish.yml` only runs
  for manually published releases.
- **Fix:** trigger `publish.yml` on `workflow_run` for `build-deb`
  (completed), no-op'ing cleanly when there is no new release — or document
  manual/`repository_dispatch` (PAT) publishing.
- **Tradeoff:** `workflow_run` also fires for skipped no-op scheduled runs,
  so the job must check `gh release view` first and exit quietly. Small
  logic cost for an actually-working chain.

## P2/P3 — hygiene, polish, latent issues

### Patch-side (all P2 unless noted)

- **Discord opus probe misses Termux's libopus** — `plugins/platforms/discord/adapter.py:447`:
  `ctypes.util.find_library("opus")` → `None` on Android (Termux deleted
  CPython's android branch — `0008-fix-ctypes-util-find_library.patch` — so
  the generic POSIX fallback applies and needs a compiler toolchain; net
  result still `None` on a typical phone). A user with `pkg install opus`
  gets "voice disabled" anyway. Fix: probe
  `$PREFIX/lib/libopus.so` as an android fallback (4 lines, strictly
  additive). Tradeoff: ~4 lines; negligible maintenance; behavior change
  only fires when the file exists. (P2)
- **`shell=True` runs under `/system/bin/sh` (mksh), not Termux's sh** —
  7 sites (`hermes_cli/bang_shell.py:117`, `agent/verify/runner.py:29`,
  `cli.py:1277`, `hermes_cli/goals.py:404`,
  `agent/command_token_source.py:54`, `hermes_cli/mcp_catalog.py:410`,
  `hermes_cli/web_routers/memory_providers.py:377`). Works (CPython on
  Android execs `/system/bin/sh -c`, verified in stdlib
  `subprocess.py:1812-1816`), but bashisms in user-typed `!` commands fail
  under mksh. Fix only the user-facing `bang_shell.py`:
  `executable=shutil.which("sh") or None`. Tradeoff: `executable=` with
  `shell=True` is slightly obscure; 7-site churn isn't worth it for a
  cosmetic-consistency win. (P2)
- **Patch 06 vs Termux:X11** — `hermes_cli/clipboard.py:87` unconditionally
  skips native clipboard tools on android. Under Termux:X11 (`DISPLAY` set,
  `xclip` installed), pristine would have used the native clipboard; now it
  always falls back to OSC 52. Narrow functional delta in an exotic-but-real
  setup. Tighter patch: keep candidates when `DISPLAY`/`WAYLAND_DISPLAY`
  is set, mirroring the pattern patch 16 already uses at
  `web_server_lifecycle.py:231`. Tradeoff: a few more lines for correctness
  in a rare configuration; OSC 52 works in most terminals, so this is
  polish, not a fix. (P2)
- **`apply.sh` verifies applicability but never the result** — even with
  `--fuzz=0`, nothing checks the post-apply tree equals the intended one
  (offset hunks, wrong `$SRC`, silent skips all pass). Fix: after phase 2,
  `diff -rq` the 26 files against a checked-in manifest (or `sha256sum -c`
  a manifest shipped beside the patches). Tradeoff: one manifest file to
  maintain; closes the fidelity loop completely. (P2)
- **`apply.sh`: no rollback on mid-apply failure** — phase 2 loop is
  unguarded; `set -e` aborts leaving earlier patches applied plus `.rej`
  files (no `.orig` — GNU patch only writes those with `--backup`). The
  dry-run is faithful so this is theoretical, but copy-and-swap (or a
  trap-and-restore) would make "all-or-nothing" literally true. Tradeoff:
  more script complexity for a window that dry-run already narrows to ~zero.
  (P2)
- **`apply.sh`: no `--fuzz=0`** — a drifted upstream could apply hunks at
  offset and still pass both phases. Add `--fuzz=0` to both invocations.
  Tradeoff: marginally more brittle against harmless whitespace drift;
  gains exactness. (P2)
- **Upstream lint allowlist** — patches 01/04/13/17 use bare `shutil.which`
  outside `hermes_platform/`, tripping upstream's
  `tests/test_managed_runtime_resolution.py` lint. Fork-only concern;
  needs allowlist entries with reasons if ever proposed upstream. (P2)
- **Patch 17 desktop delta** — PATH-resolved bash may differ from
  `/bin/bash` (e.g. Homebrew bash on macOS). Harmless. (P2)
- **Patch 10 win32 gap** — the None-guard doesn't cover the win32-only
  `psutil.Process(proc.pid).resume()` at `processes.py:128`; unreachable
  on Android. Not a phone bug. (P2)
- **Headed-Chromium branch (downgraded P2 → P3)** —
  `tools/browser_tool_real_profile.py:199`: on android the display check
  admits headed mode, but the launch is unreachable via the supported flow
  (browser detection fail-closes: `browser_connect.py:308-311` →
  `xdg-settings` absent → `None`). Worst realistic case is a fast clean
  error, not a hang. The one-line fix (admit `"android"` alongside
  `"linux"`) remains correct and harmless. (P3)
- **tzdata** — `hermes_time.py:109-127` / `hermes_cli/config.py:1076-1110`:
  with no tz database (stock Termux — termux-packages declined a tzdata
  package by design; CPython's `zoneinfo` doesn't search
  `/system/usr/share/zoneinfo`), a configured IANA timezone degrades to
  server-local with only a WARNING in the gateway log — including cron
  schedules. Fix options: vendor the pure-Python `tzdata` wheel in `site/`,
  or document `pip install tzdata` / `TZPATH`, or surface it in
  `hermes doctor`. Tradeoff: vendoring adds ~1 MB and a data-update burden;
  documenting is free but relies on the user. (P3; on-device behavior
  UNVERIFIED — needs `python3 -c "from zoneinfo import ZoneInfo;
  print(ZoneInfo('Asia/Jakarta'))"` on the phone.)
- **Process title never set on the phone** — `_set_process_title`
  (`hermes_cli/main.py:215-234`) skips entirely on android. Cosmetic; an
  android lane (`CDLL("libc.so")` + `prctl`) is P3 polish. (P3)
